## 3. New layout-aware representation

The representation is PDF-specific and lives in the PDF layer. It models
the physical layout of a page and deliberately performs **no**
reconstruction (no paragraphs/headings/columns/reading-order/header-footer
logic — those are M2.2+).

Four nested, **immutable** (`frozen=True`, `slots=True`) dataclasses:

* `TextSpan` — one run of text with the same font and style.
  - `text`, `bbox`, `font_name`, `font_size`, `font_flags`, `raw_flags`,
    `color`.
* `TextLine` — one physical line, `text`, `bbox`, `order` (dense 0-based
  line index within its block, in extraction order), `spans`, `direction`
  (writing direction `(cos, sin)`), `writing_mode`.
* `LayoutBlock` — one PyMuPDF "dict" text block: `text`, `bbox`, `order`
  (dense 0-based index among the page's *text* blocks in extraction order),
  `number` (PyMuPDF's per-page block numbering, which includes image
  blocks), `lines`.
* `LayoutPage` — one PDF page: `page_number` (1-based), `page_width`,
  `page_height`, `blocks`, `image_block_count`.
* `PageLayout` — whole-document result: `pages`, plus document-wide
  `block_count` / `image_block_count` totals (`None` when the document has
  no content blocks).

Every level exposes `x0/y0/x1/y1` and `width`/`height` properties derived
from `bbox`.

Supporting API:
* `FontFlags(IntFlag)` — decoded PyMuPDF span flag bits
  (`SUPERSCRIPT_OR_SERIF`, `ITALIC`, `SERIFED`, `MONOSPACED`, `BOLD`,
  `REVERSED`), plus `decode_font_flags(raw)`.
* `valid_bbox(bbox)` — asserts the documented geometry convention.
* `extract_page_layout(source)` — path **or** open PyMuPDF `Document`; with
  a path the file is opened and closed inside the call, with a `Document`
  the caller keeps ownership (same contract as `analyze_pdf`/`extract_book`).

## 4. Coordinate convention

Documented in the module docstring and on the model classes:

* **Origin**: top-left corner of the page (PyMuPDF page space).
* **x-axis** grows rightwards; **y-axis** grows **downwards**.
* **Units**: PDF points (1/72 inch).
* A bounding box is the **inclusive** extent of its content:
  `x1 >= x0`, `y1 >= y0`, `width == x1 - x0`, `height == y1 - y0`.
* `page_width`/`page_height` describe the page rectangle
  `(0, 0, page_width, page_height)` in the same convention.
* **Page numbers** are 1-based physical PDF page indices (page 1 = first
  page), matching the rest of `kindle_converter.pdf`.

The convention is preserved as-is from PyMuPDF — no silent coordinate
transformation is performed.

## 5. Integration with the existing extractor

The pipeline is now:

```
PDF
  ↓
PDF extraction boundary: extract_page_layout()   (src/kindle_converter/pdf/layout.py)
  ↓
layout-aware intermediate representation (LayoutPage / LayoutBlock / TextLine / TextSpan)
  ↓
M1 paragraphized extraction (src/kindle_converter/pdf/extractor.py, unchanged semantics)
  ↓
domain Book model (kindle_converter.document)
  ↓
EPUB generation (kindle_converter.epub)
```

`extractor._extract_pages(doc)` now calls `extract_page_layout(doc)` once,
then derives its raw lines from each page's `LayoutBlock`/`TextLine`
objects (via `_raw_lines`). The M1 normalization, duplicate-line
deduplication, paragraph grouping (`_same_paragraph`), and reflow logic are
untouched, so the extracted `Book` is byte-identical to before. This gives
later milestones a single, layout-aware source of truth at the extraction
boundary without replacing the M1 pipeline.

## 6. Backward-compatibility approach

* `kindle_converter.convert_pdf_to_epub()` and `pdf.extract_book()` work
  unchanged (all M1 tests and the end-to-end pipeline tests pass).
* `pdf/__init__.py` keeps every existing export; the new symbols are added.
* The layout layer reuses the existing `PDFReadError`/`EmptyPDFError`
  exceptions and the analyzer's document-ownership contract.
* The `document` domain model (and therefore EPUB generation) remains
  PDF-geometry-free — no PDF coordinates leak into the book model.

## 7. Tests added — `tests/test_pdf_layout.py`

Deterministic synthetic PDFs built with PyMuPDF only. Covers:

1. A simple PDF page produces typed layout blocks (`LayoutPage` → `LayoutBlock` → `TextLine` → `TextSpan`).
2. Page number is preserved (`1, 2, 3`; each page's text mentions its own page number).
3. Bounding boxes are preserved on every level (block/line/span).
4. Bbox internals are consistent: `width == x1 - x0`, `height == y1 - y0`, `valid_bbox` passes.
5. Text content is preserved (block/line/span join correctly).
6. Font metadata is preserved when provided: font name, size, decoded flags (`BOLD`/italic), raw flags, color.
7. Source extraction order/index is preserved: block `order` and line `order` are dense ascending; page text order is preserved.
8. Multiple blocks on a page are distinguishable (title/body/footer bboxes, sizes, fonts, orders).
9. Multiple pages retain their page association and document totals.
10. Existing M1 extraction tests continue to pass (full suite run, below).
11. Existing PDF→EPUB pipeline tests continue to pass (full suite run, below).

Plus robustness: missing/corrupt files raise `PDFReadError`, zero-page PDFs
raise `EmptyPDFError`, open-`Document` ownership is respected, and repeated
extraction is deterministic. Unit tests for `decode_font_flags` and
`valid_bbox` cover edge inputs (e.g. `None`, negative, `bool`).

## 10. Architectural decisions / limitations relevant to M2.2

* **Consumers use raw "dict" extraction order.** `LayoutBlock.order`,
  `TextLine.order`, and block `number` all reflect PyMuPDF's stream order,
  which is *not* reading order for multi-column/complex pages. M2.2 is
  expected to re-sort using the preserved geometry. The `direction` field
  (RTL-aware) and per-page block numbering are retained to support that.
* **Geometry must not be reinterpreted.** Because the coordinate system is
  top-left with y-down, M2.2 sorting must not assume PDF bottom-left
  conventions; the module documents this explicitly.
* **Font metadata may be missing.** PyMuPDF normally provides font
  name/size/flags, but the models degrade gracefully to `None` (size/name)
  or `FontFlags(0)` (flags) rather than fabricating values. M2.4 heading
  detection must treat absent font metadata as missing, not as "plain".
* **Flag semantics are capability, not usage.** A bold font reports
  `FontFlags.BOLD` even for ordinary text; M2.4 should combine flags with
  the font name heuristically.
* **Line/span grouping is PyMuPDF's.** Block grouping (visual closeness)
  and span splitting (font/style changes) are taken from PyMuPDF as-is;
  this guarantees the existing extractor needs no separate re-derivation.
* **No new dependencies.** PyMuPDF's `"dict"` layout is the single source
  of truth; nothing new was introduced.
