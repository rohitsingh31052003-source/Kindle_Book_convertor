# M8.2 Implementation Report — Windows Distribution

## 1. Summary

M8.2 prepares the existing M7 Windows packaging for its eventual first public
GitHub Release by establishing a **clean, verified, reproducible Windows
distribution artifact** and the build/verification/documentation workflow that
supports it — without redesigning the application, the packaging system, or any
conversion functionality.

The M7 packaging (M6.5 PyInstaller onedir bundle `dist/KindleBookConverter/`
built by `build_tools/build_windows.py` and verified by
`build_tools/verify_windows_package.py`) was inspected and reused unchanged.
The distribution gap was that a GitHub Release must host *single files*, while
the artifact is a folder. M8.2 closes that gap with a **reproducible ZIP
archive** of the verified bundle plus its **SHA-256 checksum**:

* `dist/KindleBookConverter-Windows-x64-0.1.0.zip` — the folder under its own
  root, 282 members, 187,512,868 bytes uncompressed → 83,118,146 bytes
  compressed;
* `dist/KindleBookConverter-Windows-x64-0.1.0.zip.sha256` — `sha256sum`
  -format checksum (SHA-256 `1d61e34b…`).

The archive is **byte-reproducible** for a given bundle (verified twice on the
real bundle), derived from the single version source, and self-verifying
through a new distribution tool. No Git commit was created.

## 2. Files created

* `build_tools/package_distribution.py` — the distribution tooling: creates
  the reproducible archive (sorted members, fixed timestamps/mode), writes the
  checksum, and verifies an archive (`archive_present`, `archive_integrity`,
  `archive_layout`, `gui_subsystem` via the shared PE parser read from
  *inside* the ZIP, `content_parity`, `checksum`). CLI mirrors the M6.5 tools
  (`--bundle`, `--zip`, `--version`, `--check`, `--no-verify`); report goes to
  `build/windows_distribution_verification.json`.
* `tests/test_windows_distribution.py` — M8.2 packaging tests (marker
  `packaging`), offline and deterministic: archive naming, checksum format,
  layout rules, content parity, GUI-subsystem detection from archive bytes,
  and a full `create_distribution`/`verify_distribution` round-trip on a
  synthetic bundle (including reproducibility, corruption, and tamper cases).
* `work report/M8.2_IMPLEMENTATION_REPORT.md` — this report.

## 4. Inspection findings (Steps 1–3 of the milestone)

Before any change, the repository was inspected as instructed. Findings:

* The M7 executable is `dist/KindleBookConverter/KindleBookConverter.exe`
  (5,903,040 bytes) inside a PyInstaller **onedir** bundle (282 files total,
  187,512,868 bytes). It requires its `_internal/` tree — the README/user guide
  already state it "does not work from the executable alone".
* Build tool: `build_tools/build_windows.py` → PyInstaller 6.22.3 freeze from a
  fresh project venv (`build/windows_build_venv`, Python 3.14.2,
  win-amd64) using the checked-in `build_tools/KindleBookConverter.spec`.
* Runtime: Python 3.14 runtime DLL, PySide6 6.11.2 (Qt DLLs + platform/
  imageformats plugins), PyMuPDF 1.28.2 (`pymupdf/*.pyd`), ebooklib 0.20/lxml,
  Pillow 12.3.0, pytesseract 0.3.13 — all bundled (12 required components).
  GUI-subsystem executable; version resource embedded from `pyproject.toml`
  via `build/version_info.txt`.
* External dependencies, exactly as documented: **Tesseract** (OCR engine, not
  bundled) and **Calibre** `ebook-convert` (AZW3, not bundled).
* Configuration: version flows from the single source `pyproject.toml`
  `[project] version = "0.1.0"` through `_meta` → version resource →
  `--sysinfo`. The bundle is git-ignored (`dist/`, `build/`).
* Packaging validation: `build/windows_package_verification.json` showed the
  M7 build passed; the M8.2 milestone re-ran it (see §8).

Because the implementation is an onedir bundle (not a one-file exe), the
simplest correct distribution format is the **one-directory bundle packed as a
ZIP archive** — not a one-file EXE, which would be a packaging redesign and is
excluded by the milestone rules.

## 5. Distribution artifact

* Name: `KindleBookConverter-Windows-x64-<version>.zip` (derived from
  `common.BUNDLE_NAME` + `PLATFORM_TAG` + the single version source; verifies
  the `Windows-x64` tag matches the toolchain: the build ran under
  `win-amd64` with a PE32+ AM64 executable).
* Checksum: `<archive>.sha256` in `sha256sum` format (`<hex>  <name>`).
* Contents: the bundle under its own root folder
  (`KindleBookConverter/KindleBookConverter.exe` +
  `KindleBookConverter/_internal/…`), so extraction reproduces the documented
  layout exactly.
* Reproducibility: members sorted by archive path; every entry carries a fixed
  timestamp (2020-01-01) and Unix mode `rw-r--r--`; compression level fixed.
  Creating the archive twice produced **byte-identical** results (same SHA-256)
  on the real bundle, and a dedicated test proves it on a synthetic bundle.

## 6. Distribution verification

`build_tools/package_distribution.py --check` re-reads the archive and checks:

| Check | Result on the shipped artifact |
| --- | --- |
| `archive_present` | ok — `dist/KindleBookConverter-Windows-x64-0.1.0.zip` |
| `archive_integrity` | ok — 282 members readable |
| `archive_layout` | ok — `KindleBookConverter/KindleBookConverter.exe` + `_internal/` present |
| `gui_subsystem` | ok — Windows GUI subsystem (2) read from inside the ZIP |
| `content_parity` | ok — archive matches bundle (282 files) |
| `checksum` | ok — SHA-256 `1d61e34b4bb24e85afd7591866d595e573bf9c309077d717212e72c843875a80` |

Report: `build/windows_distribution_verification.json`, `"passed": true`.

The distribution layer deliberately does **not** re-run the frozen executable:
bundle-level identity/smoke execution remains the M6.5 verifier's job (one
implementation, reused by `release_check.py --package`), and the release places
the distribution step *after* it.

## 8. Bundle re-verification (M6.5 gate)

The existing M7 bundle was rebuilt/verified at M7 time (passed). M8.2 re-ran
the M6.5 verifier against the bundle from the current repo state:

* static checks `ok`: artifact, GUI subsystem, version resource 0.1.0, 12
  runtime components, no dev artifacts, no dev paths;
* `isolated_sysinfo` and `isolated_launch` `ok` (frozen identity + all five
  dependencies, headless window);
* `smoke_novel_basic` `ok` (0w/0e);
* `smoke_scanned_book` / `smoke_mixed_text_image` **skip**: genuine OCR
  conversions **succeeded** because Tesseract is now installed
  (`C:\Program Files\Tesseract-OCR\tesseract.EXE`) — the designed outcome when
  OCR is available, reported honestly (the M7 run had recorded the graceful
  unavailability path instead);
* `smoke_azw3` `ok` (EPUB + AZW3 via installed external Calibre).

## 9. M6.5/M7 packaging compatibility

Explicitly confirmed: the packaging system is preserved and reused. The spec,
`build_windows.py`, `verify_windows_package.py`, the smoke harness, `_meta`,
`pyproject.toml`, and the version single-sourcing were **not** modified. The
only `common.py` change is additive (`pe_subsystem_bytes` refactor with
identical path behavior, plus the three new distribution helpers). A one-file
rebuild was rejected because the milestone forbids redesigning a working
packaging implementation.

## 10. Known limitations

* The distribution is a ZIP; there is no installer, no code signing, no
  Auto-Update, and no clean separate-machine claim — all consistent with the
  documented limitations and scope (no telemetry / cloud / installer features).
* The archive name embeds the version, so bumping `pyproject.toml` renames the
  artifact; the release checklist references `<version>` rather than a literal.
* `_tmp_res.xml` (a tracked pytest-JUnit residue from 2026-09-18) remains in
  the repository untouched; it is outside this milestone's scope and was not
  silently removed (per milestone rules). Note flagged for the manual review.
