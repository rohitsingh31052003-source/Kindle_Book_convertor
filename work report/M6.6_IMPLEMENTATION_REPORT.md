# M6.6 Implementation Report

## 1. Summary

M6.6 turned the repository into a release-ready project without changing any
converter functionality. It adds the final user documentation, the developer
documentation, an expanded Windows packaging/release guide, a release
checklist, a changelog, single-source-version validation for release
documentation, and a lightweight release validator that reuses the M6.5
package verifier. `pyproject.toml` remains the single authoritative version
source (established in M6.5); M6.6 only adds drift guards around it. The
README is finalized as the primary landing page, with M6.6 and therefore M6
marked complete in the roadmap.

No production conversion code was touched. No Git commit was created.

## 4. Versioning

The single authoritative version source is unchanged from M6.5:
`pyproject.toml` `[project] version = "0.1.0"`. It already fed the package
metadata, the runtime `kindle_converter.__version__`, the Windows executable
version resource, and the M6.5 verification. M6.6 adds release-documentation
consistency so no second manual version constant is created:

* `tests/test_windows_packaging.py` (M6.5, marker `packaging`) already guards
  package metadata / runtime / identity single-sourcing.
* `tests/test_release_docs.py` (new, marker `docs`) now guards the changelog
  head (`CHANGELOG.md` `## [0.1.0]`) against `pyproject.toml`, and the
  release checklist against pinning its own version literal. To bump the
  version a developer edits `pyproject.toml` and adds a changelog entry; the
  `packaging` and `docs` suites fail if any consumer drifts.
* `build_tools/release_check.py` reports `changelog_consistency` and
  `version_available` as release gates.

## 6. Release validation

`build_tools/release_check.py` is the new lightweight release validator. It
reuses the existing M6.5 infrastructure rather than duplicating it:

* repository gates are pure and offline: required release files exist,
  version available, changelog head matches the single version source, README
  references every required documentation file, README roadmap marks M6.6/M6
  complete and marks no future milestone complete, and git tracks no release
  directories (`build/`, `dist/`, `venv/`, `output/`, `generated/`);
* `--package` reuses `build_tools.verify_windows_package.verify` — the one
  M6.5 package-verification implementation — against the built artifact;
* `--print-commands` prints the authoritative test commands consumed by the
  release checklist;
* the report is deterministic (no network, no timestamps, no machine paths in
  the JSON), verified by a test that two runs produce identical output.

The redundant docs-drift guards live in `tests/test_release_docs.py`
(`pytest -m docs`), so ordinary test runs catch documentation drift.

## 7. Release checklist

`docs/release-checklist.md` is the release checklist. It splits the process
into **required release gates** (1–13: clean repo, selected version,
documentation current, full/regression/quality/performance suites, Windows
build, package verifier, release validator with `--package`, artifact
inspection, version consistency, release notes) and **optional /
environment-dependent gates** (14–19: native smoke, scanned/mixed behavior,
real Tesseract path, Calibre/AZW3 path, isolated local verification, actual
clean-machine verification). It explicitly states that the repository does not
claim a separate-machine clean test and records that setting for each
environment-dependent gate.

`CHANGELOG.md` uses a Keep-a-Changelog style with a single `## [0.1.0]`

## 10. M6.5 compatibility

Explicitly confirmed: the M6.5 packaging system is preserved and reused
unchanged. The build (`build_tools/build_windows.py`), the spec, the verifier
(`build_tools/verify_windows_package.py`), the smoke harness
(`kindle_converter/ui/smoke.py`), the version metadata path
(`pyproject.toml` → `_meta` → `build/version_info.txt` → executable version
resource), and `tests/test_windows_packaging.py` were not modified. M6.6 only
*reads* them (via `build_tools/common`) and lists their authoritative commands
in the release checklist. No packaging-behavior change was necessary.

## 11. Known limitations

New limitations discovered during M6.6: none in the converter. The M6.6
exercise re-confirmed the documented product limitations (recorded in the
README "Known limitations", the user guide, and the changelog): single-chapter
EPUB output, non-heading document titles, best-effort complex-layout reading
order, no OCR recognition correction, AZW3 as best-effort external conversion,
no fixed-layout/KFX output, no drag-and-drop/cancellation, no separate-machine
clean verification, and no telemetry/cloud features.

One release-engineering caveat is documented rather than hidden: the strongest
performed remote-execution check is the **isolated local** run of the frozen
artifact; a true clean-machine check is an environment-dependent optional gate
that this repository does not claim to have performed.
