# M3.2 Implementation Report - PDF Page Rendering

## 1. Summary

Implemented M3.2: a clean, reusable PDF **page rendering layer** that rasterizes
PDF pages into deterministic RGB raster images (PyMuPDF pixmaps) at an explicit,
validated DPI. The renderer is independent of OCR: it is strictly
`PDF page -> raster image`, ready for M3.3 to consume. No OCR processing, no OCR
preprocessing (grayscale, thresholding, deskewing, cropping, ...), and no
mixed-document OCR routing were implemented.

Key additions:

- **`render_page()`** - render one (1-based) PDF page at a given DPI.
- **`render_pages()`** - sequential convenience generator over a whole document,
  yielding one rendered page at a time (bounded memory).
- **`RenderedPage`** - frozen, slots-based value object carrying the 1-based page
  number, the rendering DPI, and the RGB pixmap (with `width`/`height` reported
  from the actual rendered pixmap).
- **Named DPI constants** - `DEFAULT_RENDER_DPI = 300`, `MIN_RENDER_DPI = 72`,
  `MAX_RENDER_DPI = 600`, with explicit `ValueError` validation.
- **`PDFRenderingError`** - renderer-specific exception for rasterization
  failures, carrying the affected page number in the message.
- 63 new deterministic tests in `tests/test_pdf_renderer.py` (all synthetic,
  PyMuPDF-generated PDFs; no internet, no fixtures, no OCR).

All 719 pre-existing tests still pass; the total suite is now **782 passed**.

## 4. Rendering Architecture

### Renderer location

`src/kindle_converter/pdf/renderer.py`. This matches the existing package layout,
where each milestone adds a focused submodule under `kindle_converter/pdf`
(`analyzer`, `layout`, `images`, ...).

### Public API

```python
render_page(source, page_number, dpi=DEFAULT_RENDER_DPI) -> RenderedPage
render_pages(source, dpi=DEFAULT_RENDER_DPI) -> Iterator[RenderedPage]
```

`source` follows the package's established convention: a path
(`str | os.PathLike`) or an already-open `pymupdf.Document`. With a path the
document is opened and closed inside the call; with a `Document` the caller
keeps ownership and the document is never closed or mutated.

`page_number` is the **1-based physical PDF page index**, matching
`PageAnalysis.page_number`, `LayoutPage.page_number`, and
`ImagePlacement.page_number` across the package.

### Output representation

```python
@dataclass(frozen=True, slots=True)
class RenderedPage:
    page_number: int
    dpi: int | float
    image: pymupdf.Pixmap  # RGB, alpha=False

    @property width  -> int  # == image.width  (actual rendered pixels)
    @property height -> int  # == image.height (actual rendered pixels)
```

The raster payload is PyMuPDF's native `Pixmap` (RGB, 3 components/pixel, no
alpha channel), because:

- it works naturally with PyMuPDF rendering,
- M3.3 can serialize it as needed (`image.tobytes("png")`, or `image.samples`
  raw RGB), without introducing a new imaging dependency,
- no Pillow or other imaging library was required.

`width`/`height` are properties reporting the pixmap's **own** dimensions, so
they are always consistent with the actual rendered image and never assume a
rounding convention.

### Page/provenance handling

Page identity is explicit and 1-based. `render_pages()` preserves page order and
numbers (page 1..N) and is a thin convenience layer over the same per-page
render path used by `render_page()`, so output is identical either way.

### DPI handling

DPI is a first-class, validated argument, converted internally to a PyMuPDF
scaling matrix:

```python
scale = dpi / 72.0            # 1 PDF point == 1/72 inch
matrix = pymupdf.Matrix(scale, scale)
```

Named constants:

| Constant | Value | Meaning |
|---|---|---|
| `DEFAULT_RENDER_DPI` | 300 | Default for subsequent OCR |
| `MIN_RENDER_DPI` | 72 | 1 point -> 1 pixel, lowest 1:1 resolution |
| `MAX_RENDER_DPI` | 600 | Cap; above it images grow quadratically with no OCR gain |

Invalid DPIs (non-numeric, non-finite, outside the range) raise `ValueError`
before any rendering occurs; nothing is silently clamped.

### PyMuPDF rendering approach

```python
page.get_pixmap(
    matrix=_build_matrix(dpi),
    colorspace=pymupdf.csRGB,
    alpha=False,
)
```

This is stock full-page rendering: no cropping, no hand-rolled rotation, no
preprocessing. Page rotation (`/Rotate`) is applied by MuPDF, so the output
matches the page's displayed orientation automatically. Annotations stay
enabled (default), which is desirable for later OCR.

## 5. Rendering Semantics

### Coordinate/orientation behavior

PyMuPDF's page renderer handles all coordinate and rotation transforms. A page
with a non-zero `/Rotate` entry is rasterized in its *displayed* orientation:
a 595x842 portrait page rotated 90 degrees renders landscape (verified:
`width > height`), a `180`-degree rotation keeps the portrait dimensions. No
custom rotation logic is introduced or needed (documented decision). Tests cover
rotation 90 and 180 explicitly.

### Page dimensions

`pixel = point * dpi / 72`, subject to PyMuPDF's actual rounding. The public
`RenderedPage.width`/`height` return the real rendered pixmap dimensions rather
than a formula, so consumers (and tests) deal with the renderer's true output.

### DPI conversion

`scale = dpi / 72` applied uniformly on both axes, preserving aspect ratio and
orientation. Exact-integer DPI choices (72, 144, ...) yield exact pixel
dimensions, which the tests assert exactly; non-exact cases are verified against
the renderer's actual output (proportional scaling relative to the 72-DPI
baseline) rather than an assumed rounding convention.

### Blank-page behavior

A page with no content renders as a valid all-white RGB pixmap (every sample
`255`); it is not skipped, errored, or special-cased. This is tested explicitly.

### Multi-page behavior

`render_pages()` is a single-pass, sequential generator: pages render one at a
time in ascending page order, each immediately after the previous, so a large
book is never fully resident in memory. It documents that path-owned documents
stay open for the generator's lifetime and are closed on exhaustion/close, while
caller-owned documents are never closed (both tested). No parallelization, no
threading, no caching.

## 6. Error Handling

| Situation | Exception |
|---|---|
| Missing/corrupt/unreadable PDF, page load failure | `PDFReadError` (reused from `analyzer`) |
| Zero-page document via `render_pages` | `EmptyPDFError` (reused from `analyzer`) |
| Invalid DPI (non-numeric, non-finite, out of range) | `ValueError` |
| Invalid page number (non-int, out of range) | `ValueError` |
| A page fails to rasterize | `PDFRenderingError` with the affected page number in the message |

`PDFRenderingError` is a focused, renderer-specific exception mirroring the
package's existing domain exceptions (e.g. `ImageExtractionError`). Rendering
failures are never silently swallowed, and no broad exceptions are converted into
an opaque generic error: `ValueError` keeps argument errors specific, while
PyMuPDF render failures surface as `PDFRenderingError` chained from the
underlying exception.

## 8. Tests

63 new tests in `tests/test_pdf_renderer.py`. All PDFs are small, synthetic, and
generated on the fly with PyMuPDF; no internet, external binaries, fixture files,
or OCR engines.

- **Basic rendering**: single-page, multi-page, native-text page, image page,
  blank page; renders are RGB pixmaps with no alpha.
- **Dimensions**: default DPI, exact 72/144 DPI dimensions, DPI-scaling formula,
  portrait/landscape, unusual page size, deterministic dimensions.
- **Page identity**: 1-based numbering, per-page content distinctness, order of
  `render_pages`, `render_pages` matches individual `render_page` calls.
- **Orientation**: portrait stays portrait, landscape stays landscape, rotation
  90 swaps orientation, rotation 180 keeps orientation.
- **Validation**: zero/negative DPI, out-of-range (below min, above max),
  non-numeric, non-finite, boundary min/max accepted, fractional accepted,
  integral float normalised to int, default constant sanity.
- **Determinism**: same page + same DPI render byte-identical samples (text and
  image pages); different DPIs differ.
- **Isolation**: rendering does not mutate page state (rect, mediabox, rotation,
  extracted text) or document state (page count, metadata); caller-owned
  documents stay open; path-owned documents close cleanly.
- **`render_pages` API**: order, eager DPI validation, `EmptyPDFError` on zero
  pages, open-document ownership.
- **Page-number validation**: 0/-1/out-of-range/non-integer rejected.
- **Input errors**: missing and corrupt files raise `PDFReadError`.
- **Public API surface**: exports present; `_`-prefixed helpers absent from
  `__all__`.

## 12. Known Limitations

M3.2 intentionally does not implement:

- **OCR processing** (M3.3) - the renderer only produces rasters; consuming them
  is out of scope.
- **OCR cleanup**, **mixed-document OCR routing**, and later M3 milestones.
- **OCR preprocessing**: no grayscale conversion, thresholding, denoising,
  sharpening, deskewing, contrast enhancement, cropping, background removal,
  text-region detection, or segmentation. Output is the raw full-page RGB raster
  at the requested DPI only.
- No caching, no parallel rendering, no disk-backed rendering (deliberately
  deferred; `render_pages` is a sequential generator to bound memory).

`RenderedPage` stores a live PyMuPDF pixmap; two renders compare equal only via
`image.samples` (pixel bytes), not via object equality - this is documented in
the tests and is the intended deterministic comparison.
