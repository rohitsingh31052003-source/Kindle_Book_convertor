## 3. Reading-order algorithm implemented

A per-page, three-phase, purely geometric ordering:

1. **Conservative column grouping.** Blocks are partitioned into connected
   components by horizontal x-overlap: two blocks join the same component
   when their x-intervals overlap by at least `COLUMN_OVERLAP_RATIO` of
   the *smaller* block's width. Blocks in obviously separate columns never
   overlap horizontally, so each column becomes its own component.
2. **Row grouping.** Within each component, blocks are primary-sorted by
   `(y0, x0, source_order)` and greedily joined into rows: a block joins
   the current row only if it vertically overlaps the previous block by
   more than `ROW_OVERLAP_TOLERANCE_PT` *and* its top edge stays within
   `ROW_TOP_TOLERANCE_PT` of it.
3. **Assembly.** Components are emitted left-to-right (by leftmost `x0`,
   then topmost `y0`, then source order); inside each component rows are
   emitted top-to-bottom, and each row left-to-right by `x0`.

Every comparison falls back to the original extraction `order` as the
final tie-breaker, so identical input always yields identical output.

## 4. How geometry is used

* **Vertical stacking** → primary sort key `y0`; rows are genuinely
  stacked blocks whose vertical intervals do not overlap.
* **Same row** → blocks whose vertical intervals overlap by more than
  `ROW_OVERLAP_TOLERANCE_PT` and whose top edges agree within
  `ROW_TOP_TOLERANCE_PT`; ordered left-to-right by `x0`.
* **Obvious columns** → x-interval overlap of blocks (gutter detection is
  implicit: blocks across a clear gutter do not overlap in x at all).
* **No exact float equality** anywhere; every geometric decision uses the
  centralized tolerance constants.

## 5. Tolerance strategy

All tolerances are named module constants in `reading_order.py`, fully
documented and covered by tests:

* `ROW_OVERLAP_TOLERANCE_PT = 2.0` — minimum vertical interval overlap
  (points) for two blocks to share a row. Absorbs sub-point noise on
  identical baselines while rejecting real row gaps.
* `ROW_TOP_TOLERANCE_PT = 8.0` — maximum top-edge delta (points) for a
  same-row match. Prevents a tall block from dragging unrelated lower
  blocks into its row (tested explicitly).
* `COLUMN_OVERLAP_RATIO = 0.5` — minimum shared horizontal interval, as a
  fraction of the smaller block's width, for two blocks to be in the same
  column component.

## 6. How source/extraction order is preserved

* The M2.1 `LayoutBlock.order` / `LayoutPage.blocks` are never mutated.
* `reconstruct_page_order(page)` returns a new *tuple* of the same
  immutable `LayoutBlock` references re-ordered for reading; the source
  `LayoutPage` is untouched.
* `OrderedBlock` carries `source_order` (the block's own original
  extraction order) alongside `page_order` (the reconstructed reading
  index); `OrderedPage.source_order(block)` provides an identity-based
  provenance lookup.
* The two concepts are distinct and both always available:
  *original PDF extraction order* = `LayoutPage.blocks` /
  `LayoutBlock.order`; *reconstructed order* = `OrderedPage.blocks` /
  `OrderedBlock.page_order`.

## 7. How obvious multi-column layouts are handled

Two columns laid out as:

```
A1 | B1
A2 | B2
A3 | B3
```

(i.e. blocks within each column overlap in x, blocks across columns do
not) produce the reading order `A1 A2 A3 B1 B2 B3`, verified both with
directly constructed dataclasses and end-to-end through
`extract_page_layout` on a synthetic interleaved two-column PDF.

**The milestone deliberately does NOT implement a universal column
detector.** When the columns are *not* obvious — for example a full-width
title or caption whose x-range bridges the gutter and merges the
components — the page falls back to a plain top-to-bottom /
left-to-right ordering rather than guessing. This conservative fallback is
documented in the module docstring and covered by a test. M2.6 can replace
the `_column_groups` step (or the components it produces) with a dedicated
column detector without changing the public reconstruction API.

## 8. Known limitations (intentional for M2.2)

* **Block-granularity only.** Reconstruction orders whole
  :class:`LayoutBlock` objects. When the layout library itself groups
  distinct visual columns/spans into a single block (e.g. adjacent cells
  drawn on the exact same baseline), M2.2 cannot split them; that needs
  span- or line-level reconstruction in a later milestone.
* **No universal column detection.** Bridging/full-width blocks disable
  column separation (conservative fallback, see section 7).
* **Row grouping is greedy and pairwise.** A tall block that spans two
  rows stays with the top row; blocks joined into one row are emitted
  left-to-right even if their heights differ.
* **No paragraph reconstruction**, line merging, heading detection,
  header/footer detection/removal, font-based semantic classification,
  table reconstruction/detection, OCR, or image placement/extraction.
  Image blocks are not ordered at all: only text blocks are reconstructed,
  and the presence of images never affects or breaks text ordering.
* **No claim of universal PDF layout reconstruction.**

## 9. Tests added — `tests/test_reading_order.py` (29 tests)

1. Simple vertically stacked blocks → top → middle → bottom.
2. Same-row horizontal blocks → left → right (including 3 on a row, and
   same-row blocks whose x-ranges overlap).
3. Floating-point noise: same-baseline blocks with sub-point y jitter
   stay one row; stacked rows with fuzzy boundaries stay separated;
   tolerance constants are positive and bounded.
4. Two obvious columns → `A1 A2 A3 B1 B2 B3` (direct construction, in a
   scrambled/real extraction order, plus an end-to-end synthetic-PDF
   variant). A full-width title briding both columns → conservative
   top-down fallback.
5. Multiple pages → pages keep page order; blocks are re-ordered per page
   only and never cross a page boundary.
6. Source order preserved → source `LayoutPage` never mutated; each
   `OrderedBlock` carries its own `source_order`; the reconstructed
   sequence is always a permutation (no block lost or duplicated);
   identity-based `source_order()` lookup; geometry/provenance exposure.
7. Determinism → identical input yields identical `OrderedLayout`; exact
   geometry ties break by source order and stay stable.
8. Empty page → valid empty result (no error).
9. Single-block page → unchanged. Plus: image-only page → empty text
   reconstruction, image count carried over, no crash.
10. Partial vertical overlap → a "staircase" band (each row's top
    overlaps the previous row's bottom) is NOT flattened into one row; a
    tall block does not drag a lower block into its row.
11. Different block sizes → mixed heights read stably top-to-bottom;
    same-row blocks with different heights stay in their row.

All tests assert observable reading order (given bounds → expected
text/order sequence), not internal helpers, so they remain valid if the
M2.6 column detector replaces the component step.

## 12. Architectural decisions relevant to M2.3 and M2.6

* **New reconstruction layer stays PDF-local.** All geometric reasoning
  lives in `kindle_converter.pdf.reading_order`; no PDF coordinates leak
  into the EPUB/domain model. The conceptual pipeline remains:
  `PDF → extraction → PageLayout → reading-order reconstruction →
  ordered layout → (M2.3 paragraph reconstruction) → domain Book → EPUB`.
* **Ordered views reference, never copy.** `OrderedPage`/`OrderedBlock`
  hold references to the immutable M2.1 dataclasses and add only ordering
  context, so M2.3 can consume the reading order without duplicating
  layout data. `reconstruct_page_order` returning a plain block tuple
  keeps the pure-ordering core independent of the view types.
* **Provenance is a first-class field.** `source_order` on every
  `OrderedBlock` and the identity-based `OrderedPage.source_order()` make
  the distinction "library's order" vs "reading order" explicit and
  inspectable for later milestones and debugging.
* **Column handling is swappable.** The column decision is isolated in
  `_column_groups` / `_same_column` behind the stable public API
  (`reconstruct_page_order`/`reconstruct_read_order`). M2.6 can introduce
  a dedicated column detector (e.g. gutter/profile-based, or span-aware
  splitting) by replacing that internal step only.
* **Conservative-by-default.** Pages whose layout is not obviously
  multi-column (bridging blocks, merged single blocks, exotic overlaps)
  degrade to a deterministic top-to-bottom / left-to-right fallback rather
  than misordering; M2.2 never guesses without geometric evidence.
* **Outside M2.2 scope**: no integration into `extract_book`/EPUB was
  added, because M2.2 must not silently change M1 output for ordinary
  documents. The reconstruction layer is independently testable and ready
  to be wired in by later milestones that own the ordering-to-content
  decision.
