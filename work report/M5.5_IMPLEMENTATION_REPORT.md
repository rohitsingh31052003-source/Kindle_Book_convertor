# M5.5 — Background Conversion with Progress — Implementation Report

## 1. Summary

M5.5 completes the desktop conversion workflow: clicking **Convert** runs the
configured application-layer `ConversionRequest` through
`ConversionApplication.convert` **in the background** on a dedicated
`QThread`, instead of blocking the GUI thread. A new QtCore-only
`ConversionWorker` (`kindle_converter.ui.worker`) owns nothing about
conversion — no analysis, PDF processing, OCR, reconstruction, EPUB
generation, validation, AZW3 conversion, cover loading, or output-path
calculation — and only calls the M5.1 application API and relays events. The
window reflects the run with three new `UiState` values
(`CONVERTING` → `COMPLETED` / `CONVERSION_FAILED`), a progress bar
(indeterminate while converting, full on success, reset on failure), status
messages driven by the application's own progress events, and
`last_result` / `last_error` accessors. M5.5 has **no cancellation**; instead
`closeEvent` waits for an in-flight conversion to finish so a running
`QThread` is never destroyed. The core library still never imports PySide6.

## 4. Worker API

```python
worker = ConversionWorker(application, request)   # application: ConversionApplication (or test double)
thread = QThread(window)
worker.moveToThread(thread)
thread.started.connect(worker.run)
worker.progress.connect(window._on_conversion_progress)   # queued
worker.succeeded.connect(window._on_conversion_succeeded) # queued
worker.failed.connect(window._on_conversion_failed)       # queued
worker.finished.connect(thread.quit, Qt.ConnectionType.DirectConnection)
worker.finished.connect(worker.deleteLater)
thread.finished.connect(lambda: window._on_conversion_thread_finished(thread))
thread.finished.connect(thread.deleteLater)
thread.start()
```

- **`ConversionWorker.run()`** — executes on the worker thread (connected to
  the QThread's `started`). Calls
  `application.convert(request, progress=callback)`; emits `succeeded` with
  the real `ConversionResult` on success, `failed` with the originating
  exception on failure, then always `finished`. Unexpected (non-`ApplicationError`)
  exceptions are logged here (where the traceback is intact) and still
  surface as `failed`, so a conversion failure never crashes the GUI thread.
- **Signals** — `progress = Signal(object)` (a `ConversionProgress`, forwarded
  verbatim from the application callback), `succeeded = Signal(object)`
  (`ConversionResult`), `failed = Signal(object)` (`Exception`),
  `finished = Signal()`. Because the worker lives in the worker thread and the
  window lives in the GUI thread, Qt delivers `progress`/`succeeded`/`failed`
  via queued connections; `finished` stops the thread immediately (direct
  connection), so thread shutdown never waits on a queued call back into the
  GUI thread.
- **Ownership** — one worker + one thread per conversion, both retained on
  the window (`_worker` / `_thread`) until the thread's `finished` fires, then
  released (`_on_conversion_thread_finished` guards by identity so a stale
  `finished` from an older conversion can never clobber a newer one). Both are
  scheduled for `deleteLater`; `_thread` is also parented to the window.

## 5. Architecture

```text
GUI thread                                  Worker thread
───────────                                  ────────────
MainWindow            QThread ──started──► ConversionWorker.run()
   │                                            │
   │  moveToThread(QThread)                     │  application.convert(request,
   │                                            │      progress=callback)     ◄─ M5.1 API only
   │  progress ──queued──► _on_conversion_progress  (status text = progress.message verbatim)
   │  succeeded ─queued──► _on_conversion_succeeded (last_result; UiState.COMPLETED)
   │  failed    ─queued──► _on_conversion_failed    (status message; UiState.CONVERSION_FAILED)
   │  finished ─Direct──► thread.quit
   │  thread.finished ───► _on_conversion_thread_finished (release refs) + thread.deleteLater
   │
   └── closeEvent: thread.wait() if a conversion is still running
```

The UI remains a thin presentation layer: conversion logic stays in the
M5.1 application boundary, the worker never touches widgets, and the core
library never imports PySide6 (guarded by a source-scan test).

## 8. Design decisions

1. **One worker + one thread per conversion, never reused.** A fresh `QThread`
   + `ConversionWorker` per request guarantees clean per-conversion state and
   deterministic teardown; the window retains both until the thread finishes.
2. **`worker.finished → thread.quit` via DirectConnection.** The thread stops
   internally the moment the worker reports done, so `closeEvent`'s `wait()`
   never deadlocks the GUI thread (there is no queued call back into the GUI
   that the wait would starve).
3. **Queued GUI delivery through real `QMetaObject` events.** The worker emits
   plain `Signal(object)` events that Qt routes to the GUI thread; `_wait_for`
   in the tests spins `processEvents` to let Qt deliver them, exercising the
   production wiring exactly.
4. **No fabricated percentage.** The progress bar is indeterminate
   (`setRange(0, 0)`) during `CONVERTING` because the application reports
   discrete `ConversionStage` events, not completion fractions; the status text
   shows `progress.message` verbatim. Full (`setRange(0,1); setValue(1)`) on
   `COMPLETED`, reset to 0 on `CONVERSION_FAILED`.
5. **No cancellation in M5.5.** The window guards instead: `closeEvent` waits
   for the running conversion (`thread.wait()`) so a live `QThread` is never
   destroyed. Cancellation and a real progress callback are future
   milestones.
6. **Retain the real result, never reconstruct.** `_on_conversion_succeeded`
   keeps the `ConversionResult` verbatim on `last_result` (M5.6 "output
   presentation" can consume it); failures keep the originating exception on
   `last_error`. Application errors display verbatim; unexpected errors
   collapse to a concise generic message (already logged by the worker).
7. **Thread-teardown correctness in tests.** A queued `thread.deleteLater`
   can outlive its owning window if the window is GC'd before `processEvents`
   dispatches it; the flow suite force-dispatches pending `DeferredDelete`
   events (`sendPostedEvents`) while the window is still alive, so no queued
   delete of the thread's C++ object is left dangling for a later test.

## 9. Known limitations

- No cancellation / no user-visible progress percentage (stages only);
  documented, deferred to a later M5 sub-milestone.
- `last_result` / `last_error` are accessors only; M5.5 does not present the
  converted output (open folder / open book), which is reserved for M5.6.
- Progress remains stage-level: the M5.1 `convert` reports `ConversionStage`
  events only, never per-page/OCR sub-progress (same limitation as M5.1).
- A deterministic GUI-thread crash (hard abort inside `processEvents`) was
  found and fixed during M5.5 development: it was a stale queued
  `DeferredDelete` for a finished conversion thread being dispatched after its
  owning window was garbage-collected (see decision 8). It is stable across
  repeated runs, but the windowing/teardown pattern should stay covered by the
  flow suite.
