# M5.1 — Application / Pipeline API — Implementation Report

## 1. Summary

M5.1 adds a UI-independent application layer,
`kindle_converter.application`, that owns the *user-facing conversion use
case* — validate a request, analyze the PDF, produce an EPUB, validate it,
optionally convert it to AZW3, and report progress — by composing the
existing M1–M4 public stage functions. It contains no PDF, OCR,
reconstruction, EPUB, validation, cover, or AZW3 algorithm of its own; all of
that remains in its existing modules. No PySide6/Qt code, threading, or UI
code was introduced.

## 4. Application API

```python
from kindle_converter.application import (
    ConversionApplication, ConversionRequest, ConversionResult,
    ConversionProgress, ConversionStage, OutputFormat, ProgressCallback,
    ApplicationError, InvalidRequestError, ConversionFailedError,
    OutputError, ValidationFailedError, AZW3OutputError,
)

request = ConversionRequest(
    input_pdf="book.pdf",            # required, must exist and be readable
    output_directory="out",          # required, must already exist
    formats={OutputFormat.EPUB},     # EPUB always; AZW3 optional, requires EPUB
    cover="cover.jpg",               # optional (path or document.Image)
    validate=True,                   # run M4.2 structural validation
    calibre_path=None,               # optional explicit ebook-convert path
)
result = ConversionApplication().convert(request, progress=callback)
```

- **Request/options** — immutable dataclass, validated at construction
  (types, non-empty formats, AZW3-requires-EPUB) and at `convert` time
  (existence/readability, directory, cover, explicit Calibre path).
  `InvalidRequestError` for anything wrong.
- **Entry point** — `ConversionApplication.convert(request, progress=...)`,
  synchronous, stateless, reusable, safe to invoke from a future UI worker
  thread. Constructor `engine=` / `renderer=` / `azw3_backend=` are
  dependency-injection seams (tests), not user configuration.
- **Progress** — optional callback receiving frozen `ConversionProgress`
  (`stage`, `message`, `current`, `total`). Stages: `ANALYSIS`, `EPUB`,
  `VALIDATION`, `AZW3`, terminal `COMPLETE`. Each stage emits start+finish;
  a failing stage emits only its start; `COMPLETE` never fires on failure.
- **Result** — frozen `ConversionResult` (`request`, `analysis` [M3.1
  `PDFAnalysis`], `epub_path`, `azw3_path`, `validation` [M4.2
  `EPUBValidationResult` or `None`], `warnings`, plus `outputs`,
  `page_count`, `document_type`, `valid` accessors).
- **Errors** — `ApplicationError` (subclass of the existing
  `pipeline.PipelineError`) with subclasses `InvalidRequestError`,
  `ConversionFailedError` (`stage`), `OutputError` (`path`),
  `ValidationFailedError` (`epub_path`, `validation`), `AZW3OutputError`
  (`epub_path`, `cause`). Underlying errors are always chained via
  `__cause__`; unexpected (programming) exceptions propagate unchanged.

## 5. Architecture

```text
UI (future) ──► kindle_converter.application ──► existing M1–M4 pipeline
                     convert()
                       ├── analyze_pdf                     (M3.1)
                       ├── convert_pdf_to_epub             (M1–M4: PDF→Book→EPUB)
                       │     (routing, OCR, reconstruction, cover, build)
                       ├── validate_epub                   (M4.2, optional)
                       ├── convert_epub_to_azw3            (M4.3, optional)
                       └── ConversionResult
```

Output contract: `<output_directory>/<input_stem>.epub` and
`<output_directory>/<input_stem>.azw3`, exposed as absolute paths on the
result. The EPUB is always written into the output directory (it is also the
AZW3 input); no temporary-directory strategy was added (explicitly out of
scope for M5.1).

## 8. Design decisions

1. **Reuse, not duplication.** The application layer calls the existing
   public stage functions; `PipelineError` is the documented home for
   orchestration-level errors, so `ApplicationError` extends it.
2. **Coarse stages.** `convert_pdf_to_epub` is treated as one `EPUB` stage
   because exposing per-page/OCR sub-progress would require re-implementing
   or modifying M1–M4 internals (out of scope). Documented in
   `progress.py`; the contract admits finer stages later.
3. **Extra read-only analysis pass.** `convert` runs `analyze_pdf` first for
   the summary/progress; the EPUB stage re-opens the file internally. A
   small, documented cost for a clean analysis summary without touching the
   pipeline.
4. **Validation errors raise; warnings are folded into `result.warnings`.**
   With `validate=False`, `result.validation` is `None` and no error is
   raised.
5. **AZW3 pre-check only.** An explicitly supplied, non-existent
   `calibre_path` fails fast as `InvalidRequestError`; Calibre discovery and
   launch remain M4.3's responsibility, reported as `AZW3OutputError`.
6. **No threading.** Synchronous, Qt-free; the future UI supplies threading.

## 9. Known limitations

- Progress is stage-level only (no per-page/OCR sub-progress; see decision 2).
- The input PDF is opened twice (analysis pass + conversion stage).
- No temporary-directory/staging strategy yet (deliberately deferred to a
  later M5 sub-milestone).
- AZW3 output requires Calibre on the system (unchanged from M4.3).
