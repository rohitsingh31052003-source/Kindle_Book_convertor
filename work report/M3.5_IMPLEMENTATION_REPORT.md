# M3.5 Implementation Report - Mixed Text/Image Document Handling / OCR Routing

## 1. Summary

Implemented M3.5: a **deterministic, per-page OCR routing layer** that decides,
from the M3.1 page classification, how each PDF page is processed. It wires
the existing M1/M2 native-text path and the M3.2/M3.3/M3.4 OCR chain together
without performing any structural reconstruction.

```text
PDF
 │
 ▼
 page analysis / classification           (M3.1, reused unchanged)
 │
 ├── TEXT ────► native text extraction    (M2.1 layout, reused)
 │
 ├── SCANNED ─► render → OCR → cleanup     (M3.2 → M3.3 → M3.4, reused)
 │
 └── MIXED ───► native text + render → OCR → cleanup (both preserved)
 │
 ▼
 per-page extracted representation        (this module's result)
 │
 ▼
 future structural reconstruction          (later milestones)
```

Key additions:

- **`PageProcessingResult`** - frozen/slots immutable value object
  (`page_number: int`, `classification: PDFType`,
  `native_text: str | None`, `ocr_text: str | None`). Native and OCR text
  are always distinct fields; they are never concatenated or merged.
- **`process_page(source, page_analysis, *, engine, renderer=None,
  dpi=...) -> PageProcessingResult`** - single-page routing.
- **`process_pages(source, analysis, *, engine, renderer=None, dpi=...,
  layout=None) -> list[PageProcessingResult]`** - document-level routing,
  one result per page in 1-based page order.
- **`PageRenderer`** - Protocol for the injected rendering step (defaults to
  the M3.2 `render_page`), mirroring `render_page`'s signature so tests can
  replace or count rendering calls.
- **72 deterministic unit tests** using synthetic PDFs and fake OCR
  engines/renderers only (no Tesseract, no pytesseract/Pillow).

Routing rules (deterministic, classification-driven):

- **TEXT** - native text extraction only. The page is never rendered and the
  OCR engine is never invoked.
- **SCANNED** - the page is rendered, OCR'd through the injected engine, and
  cleaned by the M3.4 cleanup layer. `native_text` is not required and stays
  `None`.
- **MIXED** - native text is preserved exactly as extracted, **and** the full
  page is rendered → OCR'd → cleaned. Both sources are kept **separately**.

M3.5 is **routing and integration, not structural reconstruction**. Nothing
here reconstructs paragraphs, detects headings, derives reading order, merges
OCR spans with native spans, identifies captions/tables, deduplicates text, or
builds document-model/EPUB elements.

## 4. Architecture

### Module location

`src/kindle_converter/pdf/processing.py`, following the package convention of
one focused submodule per concern (`analyzer.py`, `renderer.py`, `ocr.py`,
`ocr_cleanup.py`, ...). Routing is deliberately **not** placed inside
`analyzer.py`, `ocr_cleanup.py`, or `pipeline.py`.

### Reuse without modification

M3.5 imports and reuses existing APIs verbatim; none of the M3.1-M3.4 modules
were modified:

| Step | Reused API (unchanged) |
|---|---|
| Classification | `PDFAnalysis`, `PageAnalysis`, `PDFType` from `models.py`; output of `analyze_pdf` (M3.1) |
| Native extraction | `extract_page_layout` + `deduplicate_layout` (M2.1 layout; the same first-pass entry `extract_book` consumes) |
| Rendering | `render_page`, `RenderedPage`, `DEFAULT_RENDER_DPI`, `MIN_RENDER_DPI`, `MAX_RENDER_DPI` (M3.2) |
| OCR | `ocr_page`, `OCREngine` (M3.3) |
| Cleanup | `clean_ocr_result` (M3.4) |

### Result representation

`PageProcessingResult` is a `@dataclass(frozen=True, slots=True)` value object:

```python
@dataclass(frozen=True, slots=True)
class PageProcessingResult:
    page_number: int
    classification: PDFType
    native_text: str | None = None
    ocr_text: str | None = None
```

Field semantics (documented in the module and locked by tests):

- `page_number` - the **1-based** physical PDF page index, carried unchanged
  from the source `PageAnalysis`.
- `native_text` - native PDF text through the M2.1 layout path, when that path
  was used (TEXT and MIXED); `None` when the route did not use native
  extraction (SCANNED). An empty string means native extraction ran but
  produced no text.
- `ocr_text` - OCR-derived text after the M3.4 cleanup pass (SCANNED and
  MIXED); `None` when no OCR ran (TEXT). An empty string means OCR ran but
  produced no text - never silently reinterpreted as a native-text page.

### Why single-page and multi-page APIs

Each is a distinct, useful entry point:

- **`process_page`** - one page given one `PageAnalysis`; renders only that
  page and extracts the layout once. Used for page-focused interaction.
- **`process_pages`** - the whole document in page order; opens/owns the
  document once, extracts the deduplicated layout once (or accepts a
  pre-built `layout=` to avoid a redundant pass), and returns one result per
  page in 1-based order. This is the efficient multi-page variant.

### Dependency injection

OCR engines are injected exactly like M3.3 `ocr_page` requires an `OCREngine`;
no hidden global engine is ever created, so routing is testable without
Tesseract. Rendering is injected through the `PageRenderer` protocol
(defaulting to `render_page`), so tests can count or replace rendering calls.
Native text optionally comes from a caller-provided pre-built `PageLayout`
(via `layout=`), defaulting to in-module extraction through the standard M2.1
path.

### Ownership / resource handling

`source` follows the package convention: a path (`str`/`os.PathLike`) or an
already-open PyMuPDF `Document`. With a path the document is opened once,
shared by layout extraction and any rendering, and closed before returning.
With a `Document` the caller keeps ownership - it is never closed or mutated.
Temporary rendered rasters are released after each page's OCR. Page identity
is 1-based and preserved in every result; page order is never changed.

## 5. Routing Rules

The complete routing primitive (`_route_page`) implements:

1. **TEXT** - return `PageProcessingResult(page_number, TEXT,
   native_text=native_text)` with `ocr_text=None`. No rendering, no OCR.
2. **SCANNED** - render (`renderer(doc, page_number, dpi=dpi)`), OCR
   (`ocr_page(rendered, engine)`), clean (`clean_ocr_result(ocr_result)`);
   `native_text` stays `None`. Result carries `ocr_text=cleaned.text`.
3. **MIXED** - native text is preserved **and** the page is rendered → OCR'd →
   cleaned, exactly like SCANNED; the two sources stay distinct.
4. Any other classification value raises `ValueError` (defensive; the M3.1
   classifier only produces TEXT/SCANNED/MIXED per page).

Determinism properties (locked by tests):

- Pages are processed strictly in their 1-based PDF order, sequentially; OCR
  is never parallelized or reordered.
- Identical input + configuration → byte-identical results (verified by running
  the same multi-page and single-page routes twice and comparing values,
  reprs, page numbers, and classifications).
- Passing a pre-built `layout=` produces exactly the same results as letting
  the module extract it internally.

## 6. Mixed-Page Strategy (the central M3.5 decision)

A `MIXED` page carries both meaningful native text and image-heavy content
(image coverage >= `IMAGE_AREA_RATIO_THRESHOLD`). M3.5 cannot yet determine
image-only regions (that requires geometric alignment between native spans and
OCR output, which is a later structural-reconstruction concern). The least
destructive deterministic strategy that fits the existing architecture is:

1. Native text of the page is preserved verbatim as `native_text`.
2. The **whole page** is rendered and OCR'd; the recognized text passes
   through the M3.4 cleanup layer and is stored as `ocr_text`.
3. `native_text` and `ocr_text` remain distinct fields - no destructive
   concatenation, no fuzzy de-duplication, no word-level merge.

Because the full-page OCR inevitably re-recognizes the page's native text too,
`ocr_text` may overlap `native_text`. That overlap is **intentional** and is
not resolved here: removing it requires semantic/geometric deduplication,
which M3.5 explicitly defers to structural reconstruction. The tests assert
the non-merge property: a MIXED result has `native_text` and `ocr_text` as
separate fields, no combined `text` attribute exists, and neither field
contains the other's content.

## 7. Native-Text Preservation

The native-text path is the existing M2.1 layout entry point:
`deduplicate_layout(extract_page_layout(doc))` - exactly the deduplicated
layout the existing `extract_book` pipeline consumes. No reading order,
paragraph, heading, header/footer, or page-number reconstruction is run here.
`process_page`/`process_pages` never files or renames the existing M1/M2
extraction pipeline.

## 8. Error Handling

Validation is eager and mirrors the existing package conventions
(`TypeError`/`ValueError`/`EmptyPDFError`/`PDFReadError`):

- `TypeError` - `analysis` not a `PDFAnalysis`, `page_analysis` not a
  `PageAnalysis`, `engine` not an OCR engine (no callable `recognize`),
  `renderer` not callable, `layout` not a `PageLayout`.
- `ValueError` - `page_number` not a valid 1-based index of the document (or
  non-`int`/`bool`); analysis with zero pages; `analysis.page_count` not
  matching `len(analysis.pages)`; document page count disagreeing with
  `analysis`; layout page count disagreeing with `analysis`; `dpi` not a
  finite number outside `[MIN_RENDER_DPI, MAX_RENDER_DPI]`.
- `EmptyPDFError` - the PDF opens but has zero pages (reused from the M3.1
  analyzer).
- `PDFReadError` - `source` cannot be read as a PDF (reused from the M3.1
  analyzer).
- `PDFRenderingError` (M3.2), `OCRError`/`OCREngineUnavailableError` (M3.3) -
  propagated unchanged with no wrapping; `ocr_page` adds page context.
- Failures are **never swallowed**: processing stops at the first failing page
  (sequential), and engine failures are never skipped. A broken OCR engine on
  a TEXT-only document is never invoked (verified by a test).

Parameter validation happens eagerly even when no page needs OCR (matching the
renderer's own eager contract), so a bad engine/renderer/dpi/layout fails
before any work is done.

Exported from `kindle_converter.pdf` (`__all__`):

Internal helpers (`_route_page`, `_extract_layout`, `_page_native_text`,

`_validate_engine`, `_resolve_renderer`, `_validate_layout`, `_validate_dpi`,
`_open_document`, `_close_if_owned`) are intentionally **not** exported
(asserted by a test) but remain importable.

Error handling: `TypeError`/`ValueError` for argument validation (package
convention), the existing `EmptyPDFError`/`PDFReadError` for document-level
failures, and the M3.2/M3.3 exceptions propagated unchanged for
render/OCR failures. No dedicated `ProcessingError` was introduced: routing is
a composition of already-named failure modes.

## 10. Tests

`tests/test_pdf_processing.py` - **72 deterministic tests**. They build
synthetic PDFs (TEXT/SCANNED/MIXED pages) via PyMuPDF and run routes with fake
engines (`_FakeEngine`, `_PerCallEngine`, `_RaisingEngine`) and a fake
renderer (`_FakeRenderer`) that records `(source, page_number, dpi)` calls.
No Tesseract, no pytesseract/Pillow, no network, no randomness.

MIXED-page construction required care: PyMuPDF auto-shrinks a 400x300 pixmap
placed in a large rect to image-area ratio ~0.33 (TEXT-classified), so the
suite's mixed pages use a 500x700 pixmap in `Rect(20, 50, 520, 750)` with 4
long text lines, yielding ~0.70 image coverage → MIXED.

Categories:

- **`TestPageProcessingResult`** (6) - fields/values, `None` defaults, frozen
  + slots, equality, repr, `None` vs `""` distinctness.
- **`TestTEXTPageRouting`** (6) - native extraction occurs; no OCR; no
  rendering; native text preserved verbatim; classification; TEXT pages never
  trigger OCR errors or engine calls.
- **`TestScannedPageRouting`** (7) - rendering occurs with the open document;
  OCR occurs; OCR cleanup occurs (`"Hello\r\nworld\x00\n\n\nSecond paragraph"`
  → `"Hello\nworld\n\n\nSecond paragraph"`, matching the M3.4 output exactly);
  native text not required (`None`); classification; empty OCR output not
  reinterpreted as native.
- **`TestMixedPageRouting`** (6) - native text preserved verbatim; full-page
  OCR performed; native and OCR text remain distinguishable; no destructive
  concatenation and no merged `text` attribute; classification; mixed OCR
  output passes through the M3.4 cleanup.
- **`TestMultiPageRouting`** (8) - a 5-page TEXT/SCANNED/MIXED/TEXT/SCANNED
  document: exact page count and 1-based numbers; per-page classifications;
  native text only on TEXT/MIXED; OCR only on SCANNED/MIXED; OCR invocation
  count; render invocation order `[2, 3, 5]`; no cross-page contamination;
  page order never reordered.
- **`TestCallCountPolicies`** (3) - TEXT-only uses no OCR/render; SCANNED-only
  uses OCR + render per page; MIXED-only uses OCR per page.
- **`TestCleanupIntegration`** (4) - scanned output cleaned; pages cleaned
  independently; end-to-end with the **real** M3.2 renderer + fake engine (the
  full render → OCR → cleanup chain); mixed output cleaned.
- **`TestErrorPropagation`** (20) - engine-unavailable propagates with page
  context; failure gets page context; processing stops at failure (no
  skipping); unknown exceptions propagate unchanged; render failure
  propagates; mixed-page OCR failure propagates; invalid page numbers
  rejected; non-`PageAnalysis`/non-`PDFAnalysis` rejected; invalid engine,
  renderer, dpi, layout rejected eagerly; layout page-count mismatch;
  analysis page-count mismatch; zero-page analysis; document page-count
  mismatch; empty PDF (`EmptyPDFError`); missing file (`PDFReadError`).
- **`TestImmutability`** (3) - result fields frozen; analysis not modified;
  page analysis not modified.
- **`TestDeterminism`** (3) - two multi-page runs identical (values, reprs);
  two single-page runs identical; pre-built layout gives identical results.
- **`TestResourceOwnership`** (2) - open `Document` stays open and unmutated
  (multi-page and single-page).
- **`TestPublicAPI`** (4) - routing API exported; internal helpers absent from
  `__all__` but importable; prior M1-M3.4 exports still present; the routing
  module imports without the OCR extra.

## 14. Known Limitations / Deferred Work

M3.5 routes pages by classification but explicitly does **not** implement:

- image-only region detection (no geometric alignment between native spans
  and OCR output);
- de-duplication of the (intentional) overlap between `native_text` and
  `ocr_text` on MIXED pages;
- caption/table/figure identification;
- merging OCR and native spans into one paragraph stream;
- reading-order reconstruction;
- paragraph/heading reconstruction;
- EPUB or document-model output from `PageProcessingResult` values
  (structural reconstruction builds on these results in later milestones).

The routing result keeps native and OCR text as distinct, order-preserving,
immutable per-page fields so a later structural layer can decide how to
combine them with full information.
